## Area 1: Генерация API-запросов по осложнениям в `harvester.py` и `configs/<id>.yaml`

### Q1.1: Когда `harvester.py` должен запускать отдельный поисковый проход по осложнениям лечения?

| Option | Description | Selected |
|--------|-------------|----------|
| Включен по умолчанию (Recommended) | Включен по умолчанию для хирургических и смешанных (консервативно-хирургических) нозологий; для чисто терапевтических переключается на сбор побочных эффектов терапии (`adverse events`) | ✓ |
| Только по явному флагу | Запускается строго только при явном флаге `surgical_focus: true` в `configs/<id>.yaml` (при `false` проход пропускается) | |
| Безусловный хирургический фильтр | Одинаковый хирургический фильтр осложнений запускается безусловно для любой нозологии | |

**User's choice:** Включен по умолчанию для хирургических и смешанных нозологий; для чисто терапевтических переключается на сбор побочных эффектов терапии (`adverse events`).

### Q1.2: Как формировать поисковый запрос к PubMed и Europe PMC по осложнениям?

| Option | Description | Selected |
|--------|-------------|----------|
| Гибрид (Recommended) | Если в YAML прописан кастомный блок `complications_queries` — используем его (для специфических осложнений конкретной операции); иначе `harvester.py` сам собирает запрос из `core_terms`/`MeSH` нозологии + стандартного хирургического блока `MeSH/tiab` | ✓ |
| Только ручной YAML | Всегда требовать ручного заполнения `complications_queries` в каждом `configs/<id>.yaml` | |
| Только автогенерация | Только автоматическая генерация запроса внутри `harvester.py` без добавления новых полей в YAML | |

**User's choice:** Гибридный режим (`complications_queries` при наличии, иначе автосборка).

### Q1.3: Как хранить сырой кэш и помечать статьи из прицельного поиска по осложнениям в базе?

| Option | Description | Selected |
|--------|-------------|----------|
| Отдельный кэш + маркер `sources` (Recommended) | Отдельные сырые кэш-файлы (`pubmed_complications.json`, `europepmc_complications.json`) + дедупликация в общую таблицу `articles` с добавлением маркера источника в колонку `sources` | ✓ |
| Смешивание сырых JSON | Сливать результаты прямо в существующие `pubmed.json` и `europepmc.json` без разделения сырого кэша | |
| Отдельная таблица статей | Хранить статьи по осложнениям в отдельной таблице `complication_articles`, не смешивая с основным корпусом | |

**User's choice:** Отдельные сырые кэш-файлы + дедупликация в общую таблицу `articles` с маркером провенанса в `sources`.

## Area 2: Фильтрация «частых» осложнений против редкой казуистики в `triage.py`

### Q2.1: Как в `triage.py` и при экстракции отделить реально частые осложнения от редкой хирургической казуистики?

| Option | Description | Selected |
|--------|-------------|----------|
| Двухконтурный учет (Recommended) | Цифры «наиболее частых» осложнений извлекать строго из выборок `N >= 20` (мета-анализы, РКИ, регистры, когорты `Tier 1–3`), а единичные клинические случаи (`Tier 4 Case Reports`) маркировать отдельно как редкую казуистику (`<0,5%`), чтобы они не искажали частотный профиль | ✓ |
| Полное отсечение Tier 4 | Оставлять в базе осложнений только частые осложнения из когорт и РКИ (`Tier 1–3`), полностью отсекая единичные казуистические кейсы (`Tier 4`) | |
| Единый общий реестр | Не разделять когортные частые осложнения и единичные кейсы `Tier 4` — сводить все в один общий реестр | |

**User's choice:** Двухконтурный учет (`N >= 20` `Tier 1–3` для частотного профиля + отдельная маркировка казуистики `Tier 4`).

### Q2.2: Меняем ли приоритет выгрузки открытых полнотекстовых XML для публикаций по осложнениям?

| Option | Description | Selected |
|--------|-------------|----------|
| Повышенный приоритет XML (Recommended) | Давать повышенный приоритет докачки полнотекстовых XML (`Europe PMC`) статьям `Tier 1–3` с тегом `complications_safety`, так как точная разбивка мелких/частых осложнений в `%` обычно спрятана в таблицах внутри полного текста, а не в абстракте | ✓ |
| Без изменения очереди | Оставить существующую очередь скачивания XML (только по `Tier` и цитируемости без приоритета для работ по осложнениям) | |

**User's choice:** Повышенный приоритет докачки полнотекстовых XML статьям `Tier 1–3` с тегом `complications_safety`.

### Q2.3: По какому правилу присваивать кластерный тег `complications_safety` в `triage.py`?

| Option | Description | Selected |
|--------|-------------|----------|
| Комбинированное тегирование (Recommended) | Статьи из прицельного прохода осложнений + универсальный хирургический словарь в `triage.py` + опциональные специфические термины осложнений конкретной операции из YAML | ✓ |
| Только из целевого прохода | Помечать `complications_safety` только статьи, пришедшие из `pubmed_complications` / `europepmc_complications` | |
| Только по YAML-словарю | Помечать только по терминам, вручную перечисленным в `configs/<id>.yaml` | |

**User's choice:** Комбинированное тегирование `complications_safety`.

## Area 3: Классификация и поля осложнения в SQLite (`extracted_complications`) и `kb_index.json` (`frequent_complications`)

### Q3.1: Как классифицировать тяжесть осложнений в таблице `extracted_complications`?

| Option | Description | Selected |
|--------|-------------|----------|
| Двойная ось тяжести (Recommended) | Универсальный класс `Clavien–Dindo` (`I, II, IIIa, IIIb, IV, V`; для консервативного лечения — эквивалент `CTCAE Grade 1–5`) + клиническая обратимость (транзиторное самокупирующееся / требует консервативной терапии / требует реоперации / стойкий дефицит) | ✓ |
| Только Clavien–Dindo | Только шкала `Clavien–Dindo` (`I–V`) без отдельного поля обратимости и функционального исхода | |
| Простая 3-ступенчатая шкала | Простая трехступенчатая шкала (легкое / среднее / тяжелое) вместо хирургического стандарта `Clavien–Dindo` | |

**User's choice:** Двойная ось тяжести (`Clavien–Dindo` / `CTCAE` + ось обратимости исхода).

### Q3.2: Где провести границу между истинным осложнением, ожидаемым транзиторным послеоперационным периодом и рецидивом болезни?

| Option | Description | Selected |
|--------|-------------|----------|
| Разделение `event_class` без дублирования рецидивов (Recommended) | Разделять полем `event_class` на «истинное осложнение» и «транзиторное послеоперационное состояние» (с указанием срока разрешения), а рецидив/неполный релиз не дублировать в осложнениях — оставлять в контуре рецидивов/реинтервенций | ✓ |
| Только ятрогении и инфекции | Считать осложнениями только ятрогенные повреждения и инфекции, полностью исключая транзиторные болевые/рубцовые состояния из `extracted_complications` | |
| Смешивать с рецидивами | Включать в таблицу осложнений абсолютно все неблагоприятные исходы, включая рецидивы болезни и технически неполное устранение патологии | |

**User's choice:** Разделение полем `event_class` (`true_complication` vs `transient_postop_sequela`) и невключение рецидивов/неполного релиза в таблицу осложнений.

### Q3.3: Как агрегировать записи из SQLite в итоговый массив `kb_index.json` в `universal_schema.py`?

| Option | Description | Selected |
|--------|-------------|----------|
| `frequent_complications` (>=1%) + `rare_critical_red_flags` (<1%) (Recommended) | Основной массив `frequent_complications` (события с частотой `>= 1%` из когорт `Tier 1–3`, ранжированные по медиане частоты отдельно для каждого метода лечения) + отдельный подблок `rare_critical_red_flags` (`< 1%`, тяжелые ятрогенные повреждения нервов/сосудов/органов) | ✓ |
| Плоский топ-10 | Единый плоский список топ-10 осложнений без порога `1%` и без выделения редких критических повреждений в отдельный подблок | |
| Порог >= 5% | Жестко включать только осложнения с частотой `>= 5%`, отбрасывая все события в диапазоне `1–4.9%` | |

**User's choice:** Основной массив `frequent_complications` (`>= 1%` по методам лечения) + отдельный подблок `rare_critical_red_flags` (`< 1%`).
